# Живой сценарий: PT → MCP → Decimal → интерфейс

Проверка 22 ноября 2026. Используются реальные PT deepseek и T-Invest MCP sandbox; входные торговые параметры явно учебные. Заявок, счетов и переводов нет. HTTP API и публичные схемы сохранены.

## Причина MCP timeout и исправление

Сравнивался один и тот же SDK/endpoint с одним токеном и TLS verify:

| Маршрут | Наблюдение |
| --- | --- |
| Env proxy | initialize 200, notifications/initialized 202, GET SSE 200; tools/list не завершился, ReadTimeout через 15.87 s |
| Напрямую | initialize 200, initialized 202, tools/list 200 SSE; доступны 68 инструментов, DELETE сессии 200, примерно 0.27 s на открытие/закрытие |

Отдельный обычный HTTP initialize работал по обоим маршрутам. Значит одного успешного initialize недостаточно для проверки потокового MCP. Наблюдение локализует сбой на proxy route при SSE; внутреннее устройство прокси не проверялось.

`TINVEST_MCP_USE_PROXY=0` — прямой sandbox transport по умолчанию. Для окружения, которому нужен egress proxy, установить `1`: тогда HTTPX использует HTTP(S)_PROXY/NO_PROXY. Настройка касается только MCP, не PT и не глобального окружения. TLS chain/hostname verify включены, токен остаётся вне проекта. Allowlist и JSON Schema аргументов проверяются до удалённого вызова.

## Полученная спецификация

Через `invest_find_instrument` выбран ровно SiZ6/SPBFUT, UID `2dd5eb6b-7a52-4186-a0ec-9f7f6ed6fbd7`. Затем выполнены `invest_get_future` и `invest_get_market_values`.

| Поле MCP | Получено |
| --- | --- |
| lot | 1 контракт |
| minPriceIncrement | 1 пункт |
| minPriceIncrementAmount | 1 в валюте расчётов |
| currency | rub |
| lastTradeDate | 2026-12-17T16:00:00Z |
| expirationDate | 2026-12-18 |
| Последняя доступная котировка | 81999 пунктов, время источника 2026-11-22T15:59:59.464801132Z |

Это последняя доступная цена sandbox с указанным временем, не обещание текущей исполнимой цены. Спецификация получена отдельно от цены и связана с инструментом/evidence_id.

Обнаружено: minPriceIncrementAmount возвращается как Quotation без вложенной currency. Адаптер теперь использует currency той же спецификации. Нет обеих валют → нет проверенного множителя; конфликт вложенной валюты и currency контракта блокирует спецификацию. Стоимость пункта = стоимость шага / размер шага через Decimal. Основание единиц: [валюта расчётов Future](https://raw.githubusercontent.com/Tinkoff/investAPI/main/src/docs/contracts/instruments.proto), [формула пересчёта фьючерсов T-Bank](https://developer.tbank.ru/invest/intro/developer/table_order_currency).

Дополнительно Risk Engine требует явные пункты в параметрах цен фьючерса и проверяет кратность входа/стопа/цели известному шагу. Это не расчёт ГО или максимального реального убытка.

## Сквозной прогон

В браузере отправлен учебный пример: long, капитал 100000 RUB, риск 1%, условный вход 100000 пунктов, стоп 99000, количество 2 контракта. Вход/стоп не выдаются за рыночные данные. Путь: frontend → HTTP → Service → PT → search → spec/quote → PT → Python Risk Engine → SQLite/HTTP → карточка UI.

Программный результат: бюджет 1000 RUB; стоимость пункта 1 RUB; условный убыток на контракт 1000 RUB; двух контрактов 2000 RUB (2% капитала); по лимиту помещается 1 контракт. В UI показано превышение лимита. Проверены desktop 1365 px, mobile 390 px, отсутствие горизонтального переполнения и JavaScript ошибок. В `spec_evidence_id` указан полученный источник спецификации. Все компоненты живые, `test_doubles=False`, HTTPX MockTransport не используется.

Пользователь явно указал стоимость PT вход/выход = 0. Для этого добавлен `LLM_ZERO_COST_CONFIRMED=1`, действующий только для PT при обеих нулевых ценах. Без подтверждения нулевые defaults по-прежнему блокируют запросы. Лимиты числа вызовов и резервируемых токенов сохраняются; общий денежный ledger между процессами не добавлялся.

Первый запрос с 2048 output tokens обрезался (`finish_reason=length`, json_invalid), до вызова MCP. Для этого smoke задано 4096 и timeout 90 s; глобальные defaults 2048/45 s не менялись. Невалидный ответ не принимался и данные не подменялись. У smoke-скрипта также исправлен ASCII JSON stdout для Windows CP1251.

Артефакты последнего прогона в игнорируемом `backend/runtime/mcp-smoke/`: `report.json`, `state.json`, `desktop.png`, `mobile.png`. Это созданный тестовый диалог с реальными источниками, не копия рабочей БД. Не коммитить runtime. Проверяющий скрипт каждый раз создаёт новый диалог, чтобы не засчитать старый результат/evidence. Если модель не запросила quote в первом ходе, выполняется один реальный уточняющий ход; не более двух пользовательских сообщений и шести запросов модели.

## Воспроизведение

Три терминала из корня (PT-ключ в env либо существующем Windows User env, sandbox — прежнее внешнее хранилище):

```powershell
# Терминал 1: изолированный backend, <=6 реальных запросов модели.
$env:LLM_MAX_OUTPUT_TOKENS='4096'
$env:LLM_TIMEOUT_SECONDS='90'
backend/.venv/Scripts/python -m backend.scripts.smoke_vertical_slice --zero-cost-pt --windows-user-key

# Терминал 2: прежний frontend на отдельном порту.
$env:API_UPSTREAM='http://127.0.0.1:18003'
$env:PORT='15173'
node frontend/dev-server.mjs

# Терминал 3: один реальный браузерный прогон, exit 0 при успехе.
backend/.venv/Scripts/python -m backend.scripts.check_live_slice
```

Для Linux убрать --windows-user-key и передать соответствующий ключ в env; CA и сеть проверяются внутри backend окружения. Сетевые/LLM проверки отделены от offline pytest. Изолированный backend создаёт временное хранилище, рабочие базы не копирует. После прогона остановить оба сервера.

## Ограничения готовности

Это доказательство одного локального сквозного сценария, а не закрытие всего CP5. Наблюдались длинный ответ модели и самовольное процентное сравнение в тексте, хотя карточка риска рассчитана Python. Нужны отдельные проверки краткости/числовых утверждений, нормализация остального evidence и политика свежести. Схема TradePlan, подтверждение, worker/уведомления, несколько процессов и VPS этим прогоном не реализованы. Чекпойнты команда не утверждала.

Повторы выявили недетерминированный лишний search и отложенный quote, а также отклонённый ответ провайдера в уточняющем ходе. Повтор того же контекста отдельным диагностическим запросом вернул HTTP 200, finish_reason=stop, валидный Reply за 26.839 s. Это не доказательство устойчивости всех диалогов. В журнал провайдера добавлены только безопасные phase/type; body/headers/exception text не логируются.

Финальный запуск `check_live_slice` завершился **exit 0 / passed** в новом диалоге `56afc3de-3a82-4031-ae13-96d6d5c0df55`, два пользовательских хода. Спецификация `036255d8-e3c7-401b-8f43-f30062e7cb3f` получена в 20:21:27 UTC; котировка содержит своё отдельное время источника. Все три вида инструментов реально вызваны (search выполнялся дважды). Финальные offline проверки: **70 passed**, check_contracts valid/no drift, frontend check, base/VPS Compose config и diff --check прошли. Старое предупреждение Starlette/TestClient осталось. Пользовательский Git author/committer сохранён; push не поручен.

Следующая итерация устранила перечисленные блокеры CP5 программными этапами, ограничением текста и проверенным PT-профилем. Новые результаты: [CP5_EVALUATION.md](CP5_EVALUATION.md). Этот документ сохраняет историю первоначального двухходового прогона.
